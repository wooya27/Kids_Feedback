# PART A. 지금까지 뭘 만들었나 (Day 1~5 복습)

## A-0. 한 문장으로

**"강사가 아이 정보·수업기록을 서버에 넣고(POST) → 필요할 때 꺼내보고(GET) → AI가 그걸 읽고 피드백을 써주는 웹 서버."**

## A-1. 제일 중요한 것 — "한 번의 요청이 흐르는 길"

이거 하나만 머리에 있으면 코드가 안 무서워져. 나머지는 전부 이 길 위의 부품이야.

```
손님 요청
   │
   ▼
① main.py        → "이 주소는 어느 라우터로 보낼까?" (교통정리)
   ▼
② router 파일     → 실제 처리 (넣기/꺼내기 로직)
   ▼
③ database.py    → DB 문 열기 (get_db)
   ▼
④ models.py      → DB에서 조회/저장 (테이블 설계도)
   ▼
⑤ schemas.py     → 주고받는 데이터 모양 검사 + 정리
   ▼
   JSON 응답
```

**말로 외우는 버전:**
> main(어디로) → router(처리) → database(연결) → models(DB) → schemas(모양) → 응답

---

## A-2. 파일이 왜 5개나 있나 (역할 = 식당 직원)

| 파일 | 식당 비유 | 하는 일 | 왜 따로 있나 |
|------|-----------|---------|--------------|
| `main.py` | 안내데스크 | 앱 켜기 + 요청을 라우터로 연결 | 입구는 하나여야 하니까 |
| `routers/*.py` | 주방 코너 | 요청 실제 처리 | 메뉴(기능)별로 나눠야 안 엉킴 |
| `models.py` | 창고 선반 설계도 | DB 테이블 모양 | DB에 뭐가 저장되는지의 "진짜 모양" |
| `schemas.py` | 주문서/영수증 양식 | 주고받는 데이터 검사 | 이상한 데이터 걸러냄 |
| `database.py` | 창고 문지기 | DB 연결 열고 닫기 | 연결 관리는 한 곳에서 |

**핵심:** 파일이 많은 건 어려워서가 아니라 **"역할별로 쪼개야 관리가 쉬워서"**야.
한 파일에 다 넣으면 수백 줄짜리 괴물이 됨. → 이게 네가 day2, day3 문서에 이미 쓴 내용이야. 잘 잡았어.

## A-3. ⭐ 진짜 핵심 — "4단계 반복 패턴"

Day 2, 3, 5는 사실 **똑같은 일을 대상만 바꿔서 반복**한 거야. 새 기능이 생길 때마다 이 4단계가 똑같이 돌아가.

```
① models.py   → 테이블 만들기      (이 데이터를 어디에 저장할지)
② schemas.py  → 데이터 양식 만들기  (뭘 받고 뭘 돌려줄지)
③ router 파일  → API 만들기         (POST 넣기 / GET 꺼내기)
④ main.py     → 라우터 연결         (import + include_router 2줄)
```

**대상만 바뀜:**
- Day 2 = 대상이 **아이(Child)**
- Day 3 = 대상이 **수업기록(LessonRecord)**
- Day 5 = 대상이 **피드백(Feedback)** + AI 호출이 끼어듦

> 💡 자신감 포인트: 너는 이 패턴을 이미 **세 번** 돌렸어. Day 6~14에도 이 패턴이 계속 나와.
> 새로운 게 나와도 "아 이거 그 4단계구나" 하고 보면 돼.

## B-2. Day 8~11 — RAG (여기가 진짜 고비 — 근데 겁먹을 필요 없음)

> 이 섹션은 "읽고 나면 자신 있게 시작할 수 있게" 최대한 자세히 풀었어.
> 한 번에 다 외우지 마. **흐름 그림 하나 + 지도 비유 하나**만 잡으면 나머진 따라와.

---

### 🎯 B-2-0. 왜 이걸 하는가 — 실제 피드백으로 비교 (동기부터)

지금 우리 AI는 **아이 정보 + 수업기록**만 보고 답을 써. 그래서 이런 느낌이야:

**[RAG 없는 지금]**
> "유리가 오늘 줄넘기 20개를 했어요. 잘했어요! 다음엔 더 열심히 해봐요."

→ 틀린 말은 아닌데 **뻔하고 근거가 없어.** 강사가 "이걸 학부모한테 그대로 보내긴 좀..." 싶은 수준.

**[RAG 붙인 후]** — AI가 "아동 칭찬 심리" 참고자료를 같이 읽고 씀:
> "유리가 20개를 성공한 것보다 **'중간에 걸려도 다시 시도한 태도'를 구체적으로 칭찬**해주세요.
> 위축형 아이는 결과보다 과정 칭찬이 자신감에 효과적입니다(참고자료 기반)."

→ **전문성이 생김.** 이 차이를 만드는 게 RAG야. "AI를 더 똑똑하게" = 이 프로젝트의 하이라이트.

---

### 🧠 B-2-1. RAG 한 문장 + 오픈북 비유

**RAG = "AI한테 답 시키기 전에, 관련 참고자료를 먼저 찾아서 프롬프트에 끼워주는 것."**

- 지금 AI = **아무것도 안 보고 시험 보는 학생** → 아는 것만, 뻔하게 답함
- RAG = **오픈북 시험 학생** → 관련 페이지를 펴서 보고 답함 → 정확하고 근거 있음

우리가 하는 일은 딱 하나: **"AI가 시험 볼 때 펴볼 책을 준비하고, 문제에 맞는 페이지를 대신 찾아서 책상에 올려주는 것."**

---

### 🗺️ B-2-2. 제일 헷갈리는 "임베딩·벡터" — 지도 비유로 확실하게

여기서 대부분 겁먹는데, 비유 하나면 끝나.

**핵심 질문: 컴퓨터는 "칭찬"이랑 "격려"가 비슷한 말인 걸 어떻게 알까?**
→ 컴퓨터는 글 뜻을 몰라. **그래서 모든 문장을 "지도 위의 점"으로 바꿔놔.**

```
        📍"결과보다 과정을 칭찬하라"
       📍"아이를 격려하는 법"          ← 뜻이 비슷하면 서로 가까이 찍힘
                                   
                            📍"줄넘기 줄 길이 조절법"   ← 뜻이 다르면 멀리 찍힘
```

- **임베딩(Embedding)** = "문장 → 지도 위 좌표(점)로 바꾸는 것"
- **벡터(Vector)** = 그 좌표값 (실제론 숫자 여러 개의 목록. 예: `[0.12, -0.83, 0.44, ...]`)
- **비슷함 찾기** = 지도에서 **점끼리 거리가 가까운지** 재는 것. 가까우면 = 뜻이 비슷함.

> 💡 핵심 안심: **점으로 바꾸는 계산(임베딩)은 AI 라이브러리가 다 해줘.** 너는 숫자를 손으로 만들 일 없어.
> 너는 그냥 `embed(문장)` 같은 함수를 부르면 좌표가 툭 나와. **원리만 "지도에 점 찍고 가까운 거 찾기"로 이해하면 끝.**

**검색이 되는 원리 (한 문장):**
> 질문("유리 피드백 써줘")도 똑같이 점으로 찍고 → 그 점에서 **제일 가까운 자료 점 3개**를 집어온다.

---

### 🔄 B-2-3. 우리 프로젝트 실제 데이터로 흐름 따라가기

참고자료 파일에 이런 문장들이 있다고 하자 (`아동칭찬가이드.txt`):

```
- 위축형 아이는 결과보다 과정을 칭찬해야 자신감이 붙는다.
- 승부욕이 강한 아이는 도전적 목표를 주면 동기가 올라간다.
- 줄넘기는 손목 스냅으로 돌려야 팔이 덜 아프다.
```

**[준비 단계 — 프로그램 켤 때 딱 1번]**
```
① 이 파일을 읽는다
② 문장 단위로 쪼갠다(Chunking)  → 조각 3개
③ 각 조각을 점으로 바꾼다(Embedding) → 좌표 3개
④ 벡터 DB에 저장 → 이제 "검색 가능한 참고자료 지도" 완성
```

**[실행 단계 — 유리 피드백 만들 때]**
```
⑤ "위축형 유리 피드백" 이라는 질문도 점으로 바꾼다
⑥ 지도에서 가까운 조각 찾기 → "위축형은 과정을 칭찬" 조각이 딱 걸림
     (줄넘기 손목 스냅 조각은 멀어서 안 걸림 → 지금 질문과 상관없으니까 정확히 걸러짐!)
⑦ 걸린 조각을 프롬프트의 rag_context 자리에 끼운다   ← ⭐
⑧ AI가 그 조각까지 읽고 피드백 작성 → B-2-0의 "RAG 붙인 후" 결과가 나옴
```

> 이게 RAG 전부야. **"쪼개고 → 점 찍어 저장 → 질문과 가까운 점 찾아 → 프롬프트에 끼움."**

---

### 🧩 B-2-4. 왜 "그냥 자료 전부를 프롬프트에 넣으면" 안 돼?

- 자료가 수십 페이지면 **프롬프트에 다 못 넣어** (AI가 한 번에 읽는 양 한계 + 돈·속도 낭비)
- 다 넣으면 상관없는 내용(줄넘기 손목 스냅)까지 섞여서 **답이 산만해짐**
- 그래서 **"이 질문에 필요한 조각만 골라 넣기"** = RAG가 존재하는 이유

### 📖 B-2-7. 미리 알아두면 든든한 용어 사전 (한 줄씩)

| 용어 | 한 줄 뜻 | 우리 프로젝트에선 |
|------|----------|------------------|
| **RAG** | 참고자료 찾아서 프롬프트에 끼워 답 시키기 | 피드백을 전문적으로 |
| **Chunk(청크)** | 긴 문서를 자른 작은 조각 | "위축형은 과정 칭찬" 한 문장 |
| **Chunking** | 문서를 조각으로 쪼개는 작업 | 자료 → 문장 단위로 자름 |
| **Embedding(임베딩)** | 문장을 지도 위 점(숫자)으로 바꿈 | `embed("...")` → 좌표 |
| **Vector(벡터)** | 그 점의 좌표값(숫자 목록) | `[0.1, -0.8, ...]` |
| **Vector DB(벡터DB)** | 점들을 저장하고 "가까운 거" 찾아주는 창고 | 참고자료 지도 보관소 |
| **Retrieval(검색)** | 질문과 가까운 조각 찾아오기 | 유리 질문 → 관련 조각 3개 |
| **rag_context** | 찾아온 조각을 담아 프롬프트에 끼우는 자리 | Day 4에 만들어둔 빈칸 |

## B-3. Day 12~14 — Streamlit (눈에 보이는 결과물, 마감)

### Streamlit이 뭐냐 & 왜 필요한가
지금은 **Swagger**(개발자용 테스트 화면)로만 눌러봤지? 남한테 보여주긴 못생겼어.
**Streamlit = 파이썬 코드 몇 줄로 웹 화면(버튼·입력창·표)을 만드는 도구.**
- HTML/CSS 몰라도 됨. `st.button("생성")` 같은 파이썬 함수로 화면이 생김.
- 목적: 강사가 **브라우저에서 아이 고르고 → 버튼 누르면 → 피드백이 화면에 뜨는** 진짜 앱 모양.

### 흐름 (지금까지 만든 걸 화면에 연결)
```
[Streamlit 화면]  강사가 아이 선택 + 버튼 클릭
      │
      ▼
   우리가 만든 API 호출 (POST /feedbacks/generate)   ← Day 5에서 만든 그거!
      │
      ▼
   돌아온 피드백을 화면에 예쁘게 표시 (st.write 등)
```

> 안심 포인트: Streamlit은 **새 로직이 아니라 "이미 만든 API에 껍데기(화면)를 씌우는 것"**이야.
> 뒤(백엔드)는 다 됐고, 앞(화면)만 붙이는 마감 작업.

- Day 12: Streamlit 기본 (화면 요소 몇 개)
- Day 13: 화면 ↔ 우리 API 연결
- Day 14: 다듬기 + 최종 마감
