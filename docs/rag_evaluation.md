# RAG 검색 평가 방법론 (P0-6)

> 핵심: 검색 품질은 **문서 개수가 아니라 '적절한 근거를 찾는가'**로 측정한다.
> 사람이 만든 정답셋(`evals/rag_questions.json`)으로 Hit@1 / Hit@3 를 재현 가능하게 산출한다.

## 1. 평가셋 구성 (`evals/rag_questions.json`)
- 총 **48문항** = 긍정 42 + 부정 6
- 범주 분포: 성향별 20 · 상황별 10 · 성장목표 5 · 학부모소통 7 · 부정 6
- 각 긍정 질문에는 사람이 매핑한 **정답 `gold_source_files`**(복수 허용).
- **부정 사례**(negative): 관련 근거가 문서에 없는 질문(줄 길이, 환불규정, 날씨 등). 검색이 `low_relevance=True`로 **안전 처리**해야 정상.
- 질문은 문서의 `## 질문` 문구를 그대로 쓰지 않고 **다르게 바꿔** 공정한 검색 테스트가 되게 함.

## 2. 지표 정의
- **Hit@1**: 가장 유사한 Top-1 청크의 `source_file`이 정답에 포함 → 맞음.
- **Hit@3**: Top-3 안에 정답 파일이 하나라도 있으면 → 맞음.
- **Top-1 vs Top-3 비교** = 바로 이 Hit@1 과 Hit@3 의 차이. (같은 신규 인덱스·같은 질문)
- **부정 안전처리율**: 부정 질문 중 `low_relevance=True`로 걸러진 비율.
- ⚠️ 옛 1문서 인덱스와 신규 15문서 인덱스는 범위가 달라 **대조군으로 섞지 않는다.**

## 3. 실행 방법
```bash
# 전제: 신규 15문서 인덱스가 빌드되어 있어야 함
docker compose exec api python -m rag.build_index          # vectors.json 재생성(102청크)
docker compose exec api python -m evals.evaluate_retrieval # Hit@1/Hit@3 측정 → evals/retrieval_results.json
```
- 결과 원시 데이터: `evals/retrieval_results.json` (각 질문의 검색 결과·점수·정답여부 포함).

### ⚠️ 결과 해석 시 반드시 함께 쓸 한계
- **Hit@1/@3 100%는 과대평가 가능성이 크다.** 지도 문서와 평가 질문을 **같은 사람(본인)이 작성**해서
  질문이 문서와 잘 정렬돼 있다(자체 평가 과적합). 이는 "검색 파이프라인이 의도대로 동작함"의 검증이지
  **편향 없는 일반 정확도가 아니다.** 제3자 질문/외부 데이터로 재평가하면 수치는 내려갈 수 있다.
- 포트폴리오에는 "Hit@1 100%"만 떼어 쓰지 말고 **위 한계와 함께** 기재한다.

### 실패/경계 사례 (정직한 분석)
- **q43 (부정, best=0.7119):** "줄넘기 줄 적정 길이?"가 유사도 0.71로 임계값 0.70을 **근소하게 초과** →
  `low_relevance`로 안 걸러짐(부정 6건 중 유일한 miss). 임계값이 약간 낮다는 신호.
  - 조치 후보: 임계값을 0.72~0.73으로 올리면 이 사례는 걸러지나, 긍정 경계 사례(예: best 0.82대)와의
    트레이드오프를 먼저 확인해야 한다. **수치를 좋게 만들려는 임의 조정은 하지 않고** 근거와 함께 변경한다.

## 5. 실패 사례 분석 루프
- `summary.failure_ids`에 **Top-3로도 못 맞춘** 질문이 모인다.
- 각 실패에 대해 `retrieved`(실제 뽑힌 출처)를 보고 원인 분류:
  - 문서 분할 문제(한 청크에 여러 주제) → 문서를 더 잘게 쪼갠다.
  - 질문 표현 문제 → 평가 질문/문서 표현을 조정.
  - 중복·유사 청크 → 다양성 제약 확인.
- 조정 후 **재평가**. 반복 튜닝한 문항 외에 일부 확인용 문항을 남겨 과적합을 점검한다.
